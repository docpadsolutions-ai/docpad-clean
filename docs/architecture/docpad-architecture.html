1. Current system architecture

DocPad is a Next.js 16 app on Vercel in front of one Supabase project. The browser does most of the work: client components query Postgres directly through supabase-js, and Row Level Security is the real security boundary. The Next.js server only handles things that need a secret: AI calls, WhatsApp, SNOMED lookups, FHIR export and backups. There is no staging environment, queue, cache tier or warehouse.

5. Database platform

Systems

  • Postgres 17 on Supabase: the only database. OLTP, analytics, vector search, scheduling and audit all run here.
  • Supabase Storage (S3-backed) for files, scoped by <hospital_id>/ path prefix.
  • Browser sessionStorage holds unsaved encounter drafts (lib/stores/encounterDraftStore.ts).
  • No Redis, warehouse, Kafka or Snowflake. The local ~/.snowflake and ~/.confluent configs are not used by this repo.

Schemas & extensions

  • public: all app tables, views and RPCs. There are no custom app schemas.
  • auth, storage, cron, supabase_migrations: platform-managed.
  • extensions: vector, pg_trgm, pgtap, digest, uuid_generate_v4.
  • pg_cron, pg_net for jobs and outbound HTTP.
  • identity_vault.aadhaar_mapping is referenced by code but created in no migration.

6. Multi-tenancy & RLS

The database uses a single shared schema with row-level tenancy. The caller's hospital is resolved from practitioners, and almost every table carries hospital_id. Child tables without that column are scoped through their parent.

-- resolve tenant (STABLE SECURITY DEFINER)
auth.uid()
  → practitioners.user_id
  → practitioners.hospital_id
  = auth_hospital_id()

-- standard policy
USING (hospital_id = (select auth_hospital_id()))

-- child table, scoped via parent
USING (encounter_id IN (
  select id from opd_encounters
  where hospital_id = auth_hospital_id()))
  • Patients additionally need has_permission(auth.uid(), 'patients', 'read').
  • Admin-only reads use _caller_is_hospital_staff_admin(hospital_id).
  • Anonymous access is limited to 7 SECURITY DEFINER RPCs, such as get_public_prescription and get_invitation_by_token.
  • Global reference tables have no tenant column: icd10_library, snomed_*, drug_interactions, insurance_companies, tpas, ipd_consent_types.
  • Two tenant tables: hospitals and organizations share UUIDs, and older FKs point at organizations. Two tables use org_id instead of hospital_id.
  • Tests: supabase/tests/rls_isolation.sql runs 50 pgTAP assertions.

8. Gaps found while mapping

These are architectural findings from reading the code. None of them was tested at runtime.

  • Backups cannot be restored. lib/backup/runHospitalBackup.ts throws away the random AES key and stores only its hash. It also needs pg_dump, which Vercel does not provide.
  • Missing edge function. components/ipd/discharge-summary-modal.tsx:830 invokes generate-discharge-summary, and no such function exists.
  • No confirmation gate on AI output. clinical_extractions.doctor_confirmed is never set to true.
  • ABDM does not run, and its skeleton does not match the v3 contract. The gateway URL is unset and abha-enrol is a mock. The endpoint paths are guesses, not the real /api/hiecm/... routes. No callback receivers exist. Encryption uses RSA where ABDM requires Fidelius ECDH. None of the 7 ABDM tables is read or written. Section 20 has the full list.
  • ABDM code has live bugs.
    • Link and consent calls send the anon key as the bearer, so every call fails with 401.
    • ABHALinkModal.tsx can write a raw Aadhaar or mobile number into patients.abha_id.
    • Consent webhook rows have no hospital_id, so RLS hides them from everyone.
    • abdm-auth returns the gateway token to any signed-in browser.
    • The webhook check passes everything when its secret is unset.
  • Reminders never sent. CRON_SECRET is not configured in Vercel.
  • Route RBAC gap. proxy.ts does not match /ipd, so the legacy IPD tree relies on RLS alone.
  • Silent key fallback. lib/supabase/admin.ts falls back to the anon key when the service role key is missing.
  • Secrets. The Gemini key was shipped in the browser bundle, and rotating it was declined (RUNBOOK §6). PHI goes to Gemini and AssemblyAI.
  • No staging. CI pgTAP suites run against production, and every step reports green when the DB secret is missing.
  • Schema drift risk. Core-table DDL is missing from the repo. hospitals and organizations both act as the tenant table.
  • Unenforced retention. hospitals.data_retention_years (default 7) is not enforced by anything. Phone numbers are stored in plain text.
Part B

Target state

The proposed architecture for running hundreds of hospitals, hospital groups and their patients on one platform. This is a proposal, not something built yet. It assumes 500 hospitals, 20 million patient registrations and 50,000 staff users over three years. Delivery is staged: a demo on 30 Oct 2026 and an MVP on 18 Dec 2026, both on today's stack, then continuous tracks toward this target (section 16).

9. Target architecture (C4 container view)

The target keeps the two strongest assets of today's build, the Next.js UI and the Postgres data model with its safety rules. It adds what is missing between them. A typed Core API owns all writes. An event backbone carries every change to the services that react to it. Every layer carries hospital context. All PHI stays in India, and the system can survive the loss of a whole region.

TargetValue
Availability99.95% for clinical core (charting, prescribing, MAR); 99.9% for other modules
RecoveryRPO 5 min or less, RTO 1 h or less, with failover to Hyderabad (ap-south-2)
Latencyp95 under 300 ms for reads and under 500 ms for writes; patient search under 200 ms
Ward offline30 minutes of charting without connectivity
ResidencyAll PHI stored and processed in India, AI inference included

What each layer is responsible for

LayerResponsibility
EdgeBlocks attacks and rate-limits each tenant before traffic reaches compute. Partners and devices authenticate with mTLS.
BFFRenders pages and holds the session. Refresh tokens never reach browser storage. Pushes live queues (beds, lab, reception) over server-sent events.
Identity & accessKeycloak authenticates staff (SSO for chains, mandatory MFA) and patients (OTP or ABHA). Cerbos authorises each action by role, hospital, facility and care relationship. Break-glass access requires a reason and alerts the DPO.

Edge agentA small container on the hospital LAN that talks to analysers, PACS and printers, and buffers data during outages.

12. Target data platform

Data has three homes, each with a different job. Postgres is the system of record for one hospital's live operations. Kafka carries every change in commit order. The lakehouse holds history and anything that compares hospitals. Hospital dashboards run from a read replica. Group and network analytics run from Snowflake on de-identified data.

Data model changes

These changes are additive and can be migrated one at a time. The biggest is separating a person from a patient registration, so that one human can be a patient at several hospitals in a group.

13. Multi-hospital operation

Platform (DocPad)
 └─ Cell  (full stack in one region,
           serves N hospital groups)
     └─ Tenant group  (chain or owner;
                       billing customer)
         └─ Hospital  (legal entity: HFR ID,
                       GSTIN, NABH, letterhead)
             └─ Facility  (branch, clinic,
                           lab, pharmacy)
                 └─ Department / ward / OT

A small platform database, the tenant catalog, maps each hospital to its cell and its database. The BFF reads it at login and caches it.

Cells limit the blast radius. One failed deployment or overloaded database affects one cell's hospitals, not all of them.

Moving a tenant from the pooled tier to the silo tier is a scripted operation: logical replication filtered by hospital_id, then a cutover.

16. MVP plan & roadmap

The delivery plan has two hard dates: a demo on Fri 30 Oct 2026 and a working MVP live with pilot hospitals on Fri 18 Dec 2026. Neither date leaves room to re-platform. Example flow: sharing records with ABDM (DocPad as HIP)

Section 20 has the full flow, with the real v3 paths and the encryption steps. In short: the gateway calls DocPad's bridge, DocPad acknowledges at once, works asynchronously, pushes encrypted bundles directly to the requester, and reports status back to the gateway.

Integration rules

  • Canonical model: FHIR R4 with NRCES profiles at the boundary. Domain modules never parse partner formats.
  • Credentials: DocPad holds one ABDM client ID and one bridge URL for all hospitals. The gateway routes calls by X-HIP-ID, which is each hospital's HFR facility ID. Each hospital also has its own NHCX participant code, WhatsApp sender, Razorpay linked account and edge agent certificate. These live in an integration_connections table, with secrets held in Secrets Manager and referenced by ARN.
  • Idempotency: every outbound request carries a key, and every inbound message is deduplicated in the inbox.
  • Verification: webhooks are rejected unless the signature checks out (gateway JWT, HMAC or mTLS). This replaces today's shared-secret check.
  • Resilience: timeouts, exponential backoff, circuit breakers and dead-letter queues with a replay console.
  • Contracts: partner sandboxes run in CI. Consumer-driven contract tests cover internal events.
  • Observability: one correlation ID follows a message from the module through the gateway to the partner. There is a dashboard per integration and per hospital.
  • Data minimisation: only the fields a partner needs leave DocPad. Identifiers are redacted before any AI call. Every outbound PHI transfer is written to audit_logs.

Encryption (Fidelius)

  1. The HIU sends keyMaterial: cryptoAlg: "ECDH", curve: "Curve25519", a public key and a 32-byte nonce.
  2. DocPad generates a fresh key pair and 32-byte nonce for each request, then computes the shared secret with ECDH.
  3. XOR the two nonces. The first 20 bytes are the HKDF salt and the last 12 bytes are the AES-GCM IV.
  4. HKDF-SHA256 derives a 32-byte AES-256 key.
  5. Encrypt each FHIR document with AES-GCM and base64 it into entries[].content, with its careContextReference and a real checksum.

Trap: ABDM's Curve25519 is BouncyCastle's short-Weierstrass form, with 65-byte uncompressed keys (04‖X‖Y). Standard X25519 libraries do not interoperate with it. That includes the @noble/curves x25519 code in lib/abdm/encryption.ts.

Recommendation: run fidelius-cli (Java) as a sidecar for the first certification. Port it to TypeScript later, and only if the port passes Fidelius's own test vectors.

ABHA APIs use a different scheme. Aadhaar, OTP, mobile and email are encrypted with RSA/ECB/OAEPWithSHA-1AndMGF1Padding using the public certificate from /profile/public/certificate.

Build or adopt

NHA publishes an official v3 wrapper (Spring Boot + MongoDB) that handles sessions, callbacks, multiple HIP IDs and a FHIR mapper. Running it in production would add a second stack and a second database holding PHI. The recommendation is to build the bridge inside the interop gateway in TypeScript. Use the official wrapper and its mock gateway as the reference and the test oracle, and use fidelius-cli as a sidecar for encryption. That keeps tenant routing, audit and RLS in one place, while the riskiest parts, crypto and contract shape, are checked against NHA's own code.
